# AGENTS.md

Additional rules for this folder. The rules of the parent `AGENTS.md` (language, way of working, git, files) apply as well.

## Project specifics
- Role: Access add-in of AccUnit (AccUnitLoader). It uses the C# core via COM registration-free, so no installation is needed.
- It can also be used as a test starter, for example from msaccess-vcs.
- It can also install the VBE add-in (`vbe-add-In/`).
- Tests must not run in parallel with one open Access application (parallel runs fail); run them one after another.
- VBA code is versioned as text export in `LocalTest.accdb.src`.
- `LocalTest.accdb.src\AGENTS.md` is generated by msaccess-vcs-addin; do not edit it.
- Tests live in `Tests\`.

## Microsoft Access / VBA
- `Option Compare Text` and `Option Explicit` in every module, test classes included. `Option Compare Text` is set explicitly so that a changed database collation can never switch string comparison or sorting to binary or another order. Declare all variables with explicit types.
- 64-bit: API declarations with `PtrSafe`, handles/pointers as `LongPtr`.
- Naming, layout and comments: see the VBA coding style. Structure (SRP, layers, event procedures without logic): see the VBA architecture rules.
  Event procedures (`Form_Load`, `cmd..._Click`, `WithEvents` handlers) only call well-named procedures (e.g. `Form_Load` -> `InitItemsForm`, `InitFilterManager`).
- Security basics (input validation, no injection, no secrets): see the secure coding rules. In Access in particular, do not pass unchecked values to `DoCmd.RunSQL`, `Eval`, `Application.Run`, `Shell` or pass-through queries.

### Forms
- Use `Me.` for methods and properties of the form, controls included (`Me.Requery`, `Me.Dirty`, `Me.txtCustomerNo`).
- Use `Me!` only for fields of the record source (`Access.AccessField`): `Me!<FieldName>`, e.g. `Me!CustomerID`.
  The `Me.<FieldName>` property is generated when the record source is set, but it can get lost on a reimport with the msaccess-vcs-addin or after other changes, which breaks compilation.
  `Me!<FieldName>` resolves the field at runtime (late binding).

### Error handling
Follow the project's own rule if there is one (e.g. a global handler such as vbWatchdog). Otherwise:
- No blanket error handling that shows the error in a `MsgBox` and then continues.
- Add local error handling only where cleanup is needed on failure (open recordsets, transactions, object references):
  save `Err.Number`, `Err.Source`, `Err.Description`, clean up, roll back transactions, then re-raise with `Err.Raise` using the saved values.
  No `MsgBox`, do not swallow the error.
- Handle expected errors specifically and locally (e.g. error 2101 when saving is cancelled, checked against a named constant); pass all others on.

### Data access
- Use DAO or ADODB. Close recordsets and objects and set them to `Nothing`.
- Prefer parameter queries / `QueryDef` parameters over concatenated SQL.
- Use dynamic SQL only when necessary and always protect it against SQL injection (never concatenate unchecked values or identifiers into SQL).
- Dates and numbers in SQL strings must be locale independent: `#yyyy-mm-dd#`, decimal point.
- Boolean values in SQL strings against ODBC-linked SQL Server tables: use `True`/`False` in the `WHERE` clause, never `-1`/`0`; Access then converts them correctly to `1`/`0` for SQL Server. Where possible build the SQL with helper methods that already handle this (e.g. ACLib `SqlTools`, if the project uses ACLib).
- Data in linked SQL Server tables/views may be read only in approved databases (see the SQL Server rules); local configuration tables are not affected.

### Working with the database file
- `.accdb`/`.mdb` are binary: prefer the exported text files (better readable and diffable); touch the binary file only when necessary.
- Exported VBA files are usually ANSI (Windows-1252) or UTF-8 with BOM: keep the encoding (umlauts!).
- Never work with more than one Access instance on the same `.accdb`/`.mdb` at the same time (MCP server, automation, or the user's own Access window).
  Before switching, release the current instance and verify that no `MSACCESS.EXE` still holds the file open (`.laccdb`); ask the user to close Access if necessary.
  Exception: if the user has opened the file in Access, you may use exactly that running instance, but only after asking and with explicit approval (valid for the current session).
  Never open a further instance on that file (no tool that starts Access itself); if a tool cannot attach to the existing instance, do not use it. Never close the user's instance.

## Access project layout and workflow (msaccess-vcs-addin)
MS Access project (Microsoft 365, 64-bit). Check the project for whether front end and tables are in one file or split.

- `<Database>.accdb`: binary, never edit directly, do not version.
- `<Database>.accdb.src/`: source export by the msaccess-vcs-addin. Work here.
  - `modules/` (`.bas`, `.cls`), `forms/`, `reports/`, `queries/` (`.sql` + metadata), `tbldefs/`.
  - The actual folder structure of the export takes precedence over this overview.
- `<Database>.accdb.src/AGENTS.md` and `vcs-agent-docs/` are **generated by the add-in and overwritten on every export**: read them (encoding, line endings, `@Folder` placement, file types), but never edit them.

### Workflow
1. Before editing: run **Export Source Files** in Access via the add-in so the source is current. If unsure, ask whether it was exported.
2. Edit only the files in the source folder where possible; otherwise use the MCP server `access`.
3. Back into the database: add-in **Build From Source** (or merge build).
4. Then compile in Access (Debug -> Compile) and test.
- Automate Access only through the MCP servers below, not with your own COM scripts.
- Before driving Access through the MCP servers, scripts or UI Automation, read `C:\dev\AgentsConfig\docs\access-automation.md`
  (experience and recipes; the rules here take precedence). Add new insights to it as they come up.

### MCP server msaccess-vcs-mcp
- Registered as MCP server in the project's `.mcp.json` or in the user scope; target database via `ACCESS_VCS_DATABASE` in `.env` (personal overrides in `.env.local`).
- Read-only tools (`vcs_export_database`, `vcs_export_object`, `vcs_list_objects`, `vcs_diff_database`, `vcs_execute_sql`, `vcs_check_vba_compiled`, `vcs_get_log`) may be used without asking.
- Writing tools (`vcs_import_object(s)`, `vcs_rebuild_database`, `vcs_compile_vba`, `vcs_set_option`) only after approval.
- Typical flow: export -> edit source files -> `vcs_import_object` -> `vcs_compile_vba` -> check `vcs_get_log` -> `vcs_export_object`.
- An approval for an import covers the compile, log check and export that follow in this flow; anything beyond it needs a new approval.
- If compilation fails, make no further changes: ask the user to run Debug -> Compile in the VBE and to report the affected line.
- Change add-in metadata/JSON files only when necessary and with a note.
- `McpAllowRunVBA` stays off; `vcs_call_vba` and `vcs_run_vba` are not used.

### MCP server access (MCP-Access)
- Registered as MCP server in the project's `.mcp.json` or in the user scope; source: https://github.com/unmateria/MCP-Access, locally at `C:\dev\tools\MCP-Access`.
- For creating and designing objects (forms, reports, controls), e.g. `access_build_form`, `access_set_multiple_controls`.
  Do not write VBA code with it (`access_set_code`, `access_vbe_*`); code is edited in the `.cls`/`.bas` files (see division of work).
- Code execution (`MCP_ACCESS_ALLOW_CODE_EXEC`) stays disabled.

### MCP server aclib-import
- Imports and updates ACLib modules (see the ACLib rules, skill `/aclib-import`).
- It attaches to a running Access instance on the database, otherwise it starts its own hidden instance and closes it after the call.
  The single-instance rule applies: release the other servers first.
- After an import, export the imported modules with `vcs_export_object` before editing them in the source folder.

### Division of work
- Before every switch between the servers (`access`, `msaccess-vcs-mcp`, `aclib-import`) run `access_close` or `vcs_end_session` (single-instance rule).
- Layout: structural changes (new forms, adding/removing controls) with the server `access`; then immediately `access_close` and `vcs_export_object`.
  Small property changes (caption, position, format) may be made directly in the `.form`/`.report` file; mention them in the summary.
- Code: edit only in the `.cls`/`.bas` files, then `vcs_import_object` -> `vcs_compile_vba` -> check log -> `vcs_export_object`.
- Never import code while a layout change in the database has not yet been exported (the import would overwrite the layout).
- Version the source folder; put `*.accdb`, `*.laccdb` and backups into `.gitignore`. Commit after each completed step, only with approval.

## AccessCodeLib (ACLib)
- ACLib provides reusable, unit-tested and widely used code modules for many areas (dynamic SQL, filters, string handling, ...).
  Prefer an ACLib module over newly generated code: it is verified and proven in use.
  Before writing your own helper code, check whether a module already provides the functionality.
- Find modules in the ACLib module catalog (`_codelib/catalog/catalog.md`, in the local ACLib repository or at
  https://github.com/AccessCodeLib/AccessCodeLib). Never guess module names or paths; if no catalog is available, ask the user.
- For dynamic SQL, use the ACLib data modules (e.g. SqlTools, FilterStringBuilder) to protect it against SQL injection
  instead of building SQL strings by hand.
- Import and update ACLib modules with the skill `/aclib-import` (aclib-import MCP server): show the plan first,
  import only after approval, then compile. Do not copy module code manually.
  Without the skill or the MCP server, ask the user to import the module with the ACLib Import Wizard.
- ACLib modules may be edited in the project when needed. Keep such changes small and tell the user about them: they have to be
  sent back to the CodeLib (export with the ACLib Import Wizard into the CodeLib), otherwise they stay local and a later
  import with `overwrite` replaces them. Do not export into the CodeLib yourself.
- Do not import test or example modules unless the user asks (tests need the AccUnit environment).

## VBA coding style
Applies to standard modules (`.bas`), class modules and code-behind (`.cls`), and form/report files
(`.form`/`.report` from the msaccess-vcs-addin, `.frm`/`.rep` from the ACLib Import Wizard).

### Naming
- Access objects with a one-letter type prefix: tables `t...` (`tCustomers`), forms `f...` (`fCustomer`).
- Controls with a type prefix (`txt`, `lbl`, `chk`, `cmd`, ...), e.g. `txtCustomerNo`, `cmdSave`.
- VBA variables, constants, procedures and classes with meaningful names **without** type prefix (`ErrNumber`, `SaveRecord`, `CustomerRepository`).
- Standard modules (`.bas`) with the prefix `mod` (`modDaoTools`, `modProjectRules`). Class modules get no prefix.
  Exceptions without prefix only where a module is used like a namespace (`AppConfig.Value`) or a special case such as `_config` applies; decide per project in the context of its use and record it in the project facts.
  Often a better solution is a self-instancing class (`VB_PredeclaredId = True`, used as `AppConfig.Value`): it needs no prefix and its procedures cannot be called without the class name.
  Use its default instance only for stateless helpers, factories or read-only configuration; logic classes do not reach for it but receive the values they need (no hidden global state, see the architecture rules).
  Keep the existing names of imported third-party code (e.g. ACLib modules).
- Procedures: verb + object (`LoadCustomer`, `CalculateTotal`); functions that return a Boolean read as a question (`IsValid`, `HasItems`).
- Interfaces start with `I` (`ICustomerRepository`); implementing classes are named after what they do (`CustomerRepository`, `CustomerRepositoryFake`).
- Test classes are named `<ClassUnderTest>Tests` (see AccUnit rules).
- Constants in `PascalCase` (no all-caps, no `c`/`k` prefix); enum names singular, members prefixed with the enum name where this avoids clashes.

### Layout
- Indent with 4 spaces (no tabs); keep the indentation style of an existing file.
- One statement per line; avoid line continuations unless they clearly help readability; lines at most ~100 characters.
- Declare variables close to their first use, one per line, always with an explicit type. No `Variant` unless required.
- Use `ByVal` for parameters unless the procedure has to change the caller's value; declare scope (`Public`/`Friend`/`Private`) explicitly.
- Module order: `Option` lines, constants and enums, private members, events, public properties, public procedures, private procedures.
- Standard modules that must not be accessed from outside the project get `Option Private Module` (after `Option Explicit`).
  Use it for internal helpers, so that their `Public` procedures stay out of other VBA projects, the macro list and `Application.Run` calls from outside.
  Do not set it on modules whose procedures are called from queries, form/report properties or macros: such calls may stop working, so check the callers first.
  Class modules have no `Option Private Module` effect; limit what they expose with `Friend` and `Private` members.
- Place objects in the `@Folder` structure used by the project (see `vcs-agent-docs`); do not invent a new structure.

### Comments
- Comments explain why, not what. No commented-out code.
- A public procedure whose name and parameters do not explain it fully gets a short comment line above it.

### Files
- Keep the encoding and line endings of existing files (usually ANSI/Windows-1252 or UTF-8 with BOM, CRLF); take care with umlauts.

## VBA architecture (SRP, layers, testability)
- **Single responsibility is the main rule.**
  - A procedure does one thing; split long procedures into named steps, a reader should grasp it without scrolling.
  - A class or module has one reason to change. When a class needs "and" to describe it, split it.
  - Treat length as a warning signal, not as a hard limit: a procedure over ~30 lines or a class over ~300 lines is a reason to check for several responsibilities.
- **Layers** (dependencies point downwards only):
  1. UI: forms and reports. Event procedures contain no logic; they call well-named procedures that only read inputs, delegate and show results.
  2. Logic: classes and standard modules with the rules of the application. No reference to forms (`Forms!...`, `Me`), no `MsgBox`, no direct database access (`CurrentDb`, `DoCmd`).
  3. Data access: own classes or modules (repository style) that read and write data, built on DAO/ADODB or the ACLib data modules.
- Apply the layers to new code with real application logic; forms that only show and edit data need no extra layers (YAGNI).
- **Testable by design:** logic receives what it needs through parameters or properties (dependency injection), not by reaching for globals or the database.
  Describe collaborators with an interface (`Implements`) when a fake is useful in tests. Logic classes keep no hidden global state.
- If the project uses AccUnit, new logic comes with tests (see the AccUnit rules).
- Put logic into classes or modules, not into form modules; a form module only wires the UI to the logic.
- Return results and raise errors; the UI layer decides how to show them.
- **Reuse before writing new code:** check the AccessCodeLib modules first, then existing project modules; write new code only if neither fits.
- Do not restructure existing code unasked. In code you touch for another reason, apply these rules to the new and changed parts; report further findings instead of fixing them.

## Unit tests with AccUnit
- Logic classes and logic modules (see the architecture rules) are covered by AccUnit tests. Forms, reports and pure wiring code are not unit-tested.
- New logic comes with tests; for a bug fix, write the failing test first. Tests belong in the same commit as the code they cover.
- Do not change existing logic without tests that protect it. If there are none, propose characterization tests in the plan;
  if the code cannot be tested without restructuring it, ask before restructuring.

### Test classes
- A test class is a class module named `<ClassUnderTest>Tests` (e.g. `OrderCalculatorTests`) and is marked with the comment `'AccUnit:TestClass` in the declaration section.
- Test classes use `Option Compare Text` and `Option Explicit` like all other modules (also if AccUnit examples show `Option Compare Database`).
- Every public `Sub` of the class is a test. `Setup` runs before and `Teardown` after each test.
- Assertions: `Assert.That Actual, Iz.EqualTo(Expected)`. Use only constraints that exist in the project's AccUnit version; do not guess names, look at existing tests or the AccUnit wiki
  (https://github.com/AccessCodeLib/AccUnit/wiki).
- Attributes are comments above the procedure or in the declaration section:
  - `'AccUnit:Row(Param1, Param2)` for parameterized tests (the test procedure receives the values as parameters)
  - `'AccUnit:TestClass:Tags(...)` / `'AccUnit:Tags(...)` to group tests, `'AccUnit:Ignore(Reason)` to skip with a reason
  - `'AccUnit:Rollback` for tests that write data (not with domain aggregate functions such as `DLookup`)
- Helper modules for tests are marked `'AccUnit:TestRelated`.
- Test names describe the behavior: `ReturnsZeroForEmptyOrder`, not `Test1`. One behavior per test; Arrange - Act - Assert, in that order, separated by blank lines.
- Tests do not depend on the content of the productive database. Create test data inside the test, or pass fakes through the interfaces of the logic.
- Tests must be repeatable and independent of each other and of the execution order.

### Running the tests
- Tests are run with AccUnit in Access (the AccUnit add-in / AccUnit-Loader); tests are not run by Claude through VBA automation.
- After writing or changing tests, state which tests are expected to pass and ask the user to run them and report the result. Do not claim that tests pass without a reported result.
- Import test modules only into projects that use AccUnit; ACLib test modules are not imported (see the ACLib rules).
